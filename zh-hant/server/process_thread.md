# 進程/線程和工作模式

- `Swoole` 異步服務器包含 `5` 種進程/線程角色：[`master`](#master)、[`manager`](#manager)、[`worker`](#worker)、[`task`](#task) 與 [`user`](#user)。
- 與此同時，它支持三種運行模式：[`SWOOLE_PROCESS`](#swoole-process)、[`SWOOLE_BASE`](#swoole-base) 和 [`SWOOLE_THREAD`](#swoole-thread)，分別對應多線程+多進程、多進程，以及多線程的工作方式。`進程/線程` 與 `運行模式` 之間具有緊密的依賴關係。提前理解它們對於學習後續章節十分重要。

## 進程/線程

### 示例

- 爲了更通俗地理解，我們可以把**異步服務器**比作一家**工廠**：
    - **master（工廠廠長）**：負責工廠的整體穩定運行，制定規則、處理重大問題。銷售前臺直接向廠長彙報。

    - **reactor（銷售前臺）**：負責接待客戶、接單登記，但不參與實際生產。客戶來了，銷售先記錄需求，再把訂單往後傳給工人，自己繼續接待下一位。

    - **manager（工廠副廠長）**：管理工人和行政事務。當廠長不在時，副廠長能承擔部分決策職責，確保工廠運轉不中斷。

    - **worker（產線工人）**：負責核心生產，真正把客戶要的產品做出來。做完後可以把成品交給銷售去發貨，但有時工人也要兼職銷售（比如小廠裏，工人自己接單、自己生產）。

    - **task（行政/後勤）**：負責處理各種非核心事務，比如整理文件、回覆郵件、協調資源。當工人忙着生產時，可以把這些雜事交給行政，讓工人一心一意造產品，不用頻繁被打斷。

    - **user（設備監控）**：不參與核心業務，只是記錄和上報設備運行情況。

### master

- **核心定位**：作爲多線程的管理與通信中樞，`master` 進程負責創建並管理多個 `reactor` 線程。

- **reactor 線程職責**：
    - 每個 `reactor` 線程專注於維護客戶端連接，處理網絡 I/O、協議解析及數據收發。

    - **數據流轉**：通過 `unixSocket` 套接字將接收到的數據拼接爲完整的數據包並轉發給 `worker` 進程，同時將 `worker` 的處理結果返回給客戶端。

    - **注意**：`reactor` 線程僅負責網絡層，**不執行任何 PHP 代碼**。

- **生命週期管理**：
    - `master` 進程負責管理整個服務的生命週期。

    - **SIGTERM**：向 `master` 進程發送該信號可停止服務。

    - **SIGUSR1**：重啓所有 `worker` 和 `task` 進程。

    - **SIGUSR2**：僅重啓 `task` 進程。

> [!IMPORTANT]
> **注意**：`master` 進程僅在 `SWOOLE_PROCESS` 模式下存在，其他運行模式中無此進程。

### manager

- **核心職責**：負責管理 `worker` 和 `task` 進程的生命週期，包括進程的創建、監控與回收。

- **信號處理**：
    - **SIGUSR1**：向 `manager` 進程發送該信號，將重啓所有 `worker` 和 `task` 進程。

    - **SIGUSR2**：向 `manager` 進程發送該信號，將僅重啓 `task` 進程。

- **BASE 模式特性**：
    - 在 `SWOOLE_BASE` 模式下，`manager` 進程接管整個服務的生命週期管理。

    - **SIGTERM**：在此模式下，向 `manager` 進程發送該信號可停止服務。

> [!IMPORTANT]
> 如果是 `SWOOLE_THREAD` 工作模式，`manager` 進程會變成 `manager` 線程，其餘不變。

### worker

- **核心職責**：`worker` 進程專注於執行所有的業務邏輯代碼。

- **SWOOLE_PROCESS 模式**：
    - **分工協作**：`worker` 進程與 `reactor` 線程分離。

    - **工作流程**：`worker` 接收由 `reactor` 線程轉發來的完整數據包，執行業務邏輯處理後，將結果返回給 `reactor` 線程，由後者發送給客戶端。

- **其他模式（如 SWOOLE_BASE）**：
    - **全權負責**：`worker` 進程集網絡 I/O 與業務邏輯於一身。

    - **工作流程**：直接負責接收客戶端數據、執行業務邏輯，並將處理結果返回給客戶端。

> [!IMPORTANT]
> 如果是 `SWOOLE_THREAD` 工作模式，`worker` 進程會變成 `worker` 線程，其餘不變。

### task

- **核心定位**：`task` 進程專爲處理異步任務而生，它將任務投遞、隊列管理及 PHP 任務處理進程整合爲一體，通過底層 API 即可輕鬆實現異步任務處理。

- **應用場景**：
    - 在傳統的 PHP-FPM 應用中，我們常需藉助 Redis 等外部隊列和後臺腳本來異步處理耗時任務，以避免阻塞主進程並維持高併發能力。

    - Swoole 的 `task` 進程正是爲了解決這一痛點，它內置了異步任務處理能力，無需依賴外部組件即可實現高效的後臺任務調度。

- **結果反饋**：
    - `task` 進程不僅負責執行任務，還支持在任務執行完畢後，將結果返回給 `worker` 進程，實現完整的數據閉環。

> [!IMPORTANT]
> 如果是 `SWOOLE_THREAD` 工作模式，`task` 進程會變成 `task` 線程，其餘不變。

### user

- **核心定位**：與其他內置進程不同，`user` 進程完全由用戶自定義。它通常用於創建特殊的工作進程，以執行監控、狀態上報或其他定製化任務。

- `user` 進程通過 [Swoole\Server->addProcess()](/zh-hant/server/methods.html#addprocess) 創建生成。

- **生命週期與穩定性**：
    - `user` 進程的生存週期與 `master` 和 `manager` 進程保持一致，具有極高的穩定性。

    - **重啓免疫**：向 `master` 進程和 `manager` 進程發送 `SIGUSR1` 和 `SIGUSR2` 時，系統不會向用戶進程發送任何信號，確保其持續運行。

    - **停止處理**：在服務器關閉（shutdown）時，系統會向用戶進程發送 `SIGTERM` 信號，以確保其被安全關閉。

- **進程託管與守護**：
    - `user` 進程由 `manager` 進程統一託管。不會觸發 [workerStop](/zh-hant/server/events.html#workerstop) 等事件。

    - **異常恢復**：如果用戶進程在運行時退出，`manager` 進程會自動檢測到並重新創建一個新的進程，確保任務的高可用性。

## 工作模式

### SWOOLE_PROCESS

- `SWOOLE_PROCESS` 模式下，所有客戶端連接均由 `master` 進程統一管理，內部實現較爲複雜，涉及大量進程間通信（IPC）與進程管理機制。該模式適用於業務邏輯極其複雜的場景：`Swoole` 提供了完善的進程管理與內存保護機制，確保即便在複雜業務邏輯下也能長期穩定運行。

- 此外，`Swoole` 在 `reactor` 線程中提供了 `Buffer` 緩衝功能，可有效應對大量慢速連接及逐字節發送數據的惡意客戶端。

**優點：**

- 連接與數據請求處理分離，避免因部分連接數據量過大而導致 `worker` 進程負載不均。

- `worker` 進程正常重啓或者發生致命錯誤退出時，已建立的連接不會被切斷。

- 支持單連接併發：只需維持少量 `TCP` 連接，請求即可在多個 `worker` 進程中併發處理。

**缺點：**

- 存在兩次進程間通信開銷：`master` 進程中的 `reactor` 線程與 `worker` 進程之間需通過 `unixSocket` 通信交換數據。

- `SWOOLE_PROCESS` 模式不支持 PHP ZTS（Zend 線程安全）。若需在 `ZTS` 環境下運行，只能使用 `SWOOLE_BASE`/`SWOOLE_THREAD` 模式，或將 [single_thread](/zh-hant/server/setting.html#single-thread) 參數設爲 `true`。

### SWOOLE_BASE

- 在 Swoole 的多種工作模式中，`SWOOLE_BASE` 通常被視爲性能最優的選擇。它採用了一種扁平化的架構設計，極大減少了進程間的交互開銷。

**優點：**

- `SWOOLE_BASE` 模式下不存在 `master` 進程的角色，僅保留 `manager` 進程（在某些極簡場景下甚至都沒有 `manager` 進程）。

- 每個 `worker` 進程身兼數職，同時承擔**客戶端連接維護**、**數據收發**以及**業務邏輯處理**的所有工作。

- `manager` 進程在 `SWOOLE_BASE` 模式下是可選的。如果設置了 [`worker_num=1`](/zh-hant/server/setting.html#worker-num) 且沒有開啓 `task` 進程或開啓 [max_request](/zh-hant/server/setting.html#max-request) 特性，底層將直接創建一個單獨的 `worker` 進程，完全不創建 `manager` 進程。

- 由於去除了 `master` 進程，數據不再需要經過進程間通信（IPC）轉發。這種直接處理機制消除了通信瓶頸，使得 `SWOOLE_BASE` 模式在性能上表現最佳。

- 代碼邏輯更加直觀簡單，減少了複雜的進程管理和調度環節，從而降低了出錯的概率。

**缺點：**

- 客戶端連接直接綁定在 `worker` 進程上。一旦某個 `worker` 進程因異常崩潰，該進程內維持的所有客戶端連接將被強制關閉。

- 客戶端連接與 `worker` 進程是靜態綁定的。對於少量的長連接客戶端，無法利用到所有 `worker` 進程的資源。例如你有 `100` 個 `worker` 進程，但是隻有 `80` 個連接，那麼肯定有 `20` 個進程是空閒的。

- 在長連接應用中，如果某些連接數據量大，其所在的 `worker` 負載會極高；而處理輕量連接的 `worker` 則處於空閒狀態，導致不同 `worker` 進程間無法實現均衡。

- 如果回調函數中存在阻塞操作，服務器將退化爲同步模式。這會導致事件循環停滯，極易引發 `TCP backlog` 隊列塞滿，從而導致拒絕服務。

### SWOOLE_THREAD

- `SWOOLE_THREAD` 是 `Swoole 6.0` 引入的全新運行模式，基於 `PHP` 的 `ZTS（Zend Thread Safety）` 能力，支持開啓多線程服務。

- 在該模式下，整個服務只存在一個進程，`worker` 進程等全部都會變成線程用於處理客戶端請求。

**優點：**

- 線程間無需藉助進程間通信（IPC），減少了額外開銷。

- 單一進程結構使 `gdb -p` 調試變得更加直觀。

- 既能享受協程帶來的高併發 I/O 編程便利，也能利用多線程實現任務並行與共享內存堆棧。

**缺點：**

- 一旦發生線程崩潰，整個進程會退出，需客戶端實現錯誤重試、斷線重連等容錯機制，並配合 `Supervisor、Docker/K8s` 實現進程自動恢復。

- `ZTS` 與 `鎖` 操作會帶來額外開銷，性能較 `NTS` 多進程模式降低約 `10%`。無狀態服務仍建議採用 `NTS` 多進程模型。

- 不支持在線程之間傳遞對象或資源類型的數據。必須使用 `Swoole` 準備的併發安全容器。

> [!IMPORTANT]
> `PHP` 必須是 `ZTS（Zend Thread Safety）` 模式，並且編譯 `Swoole` 的時候需要加入 [`--enable-swoole-thread`](/zh-hant/start/install.html#通用功能選項) 模式。
